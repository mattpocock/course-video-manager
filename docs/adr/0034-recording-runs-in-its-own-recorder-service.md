# Recording runs in its own recorder service

> **Note (superseded in part):** decision 2 and the first consequence, the detached lifecycle, are superseded by [ADR 0035](0035-the-recorder-service-starts-and-stops-with-pnpm-dev.md): the service now starts and stops with `pnpm dev`. The rest stands.

> **Note (superseded in part):** the Spacedesk display's shape in decision 9 (16:9, 1920x1080, the Short showing its left square) is superseded by [ADR 0043](0043-a-shorts-spacedesk-screen-is-1080x1080.md): the display is 1080x1080 and a Short draws all of it. The rest of decision 9 stands.

> **Note (amended):** where the recorder client saves a speech's Clips is amended by [ADR 0044](0044-the-cvm-recorder-is-an-adapter-onto-obs-clip-logic.md): it asks the editor for its Insertion Point when the speech ends, and keeps none of its own.

> **Note (renamed):** the "new recorder" this ADR describes is now the **CVM recorder**, stored as `video.recorder = 'cvm'` (#1993). The wording below is kept as decided.

Today OBS records every **Video**, and the app reads the file it writes. The new recorder (PRD #1994, decisions in #1993) replaces OBS for Videos that choose it: ffmpeg.exe 8.0.1 on Windows records the camera, the screen and the mic as three files for one **Recording Session**, on one shared clock. Something has to start those ffmpeg processes, hold them while a Recording Session runs, read their silence detection, and stop them cleanly. This ADR records where that runs.

## Decision

1. **Recording runs in the recorder service, a small long-running process of its own in WSL** (`apps/local/recorder-service/`), in the same family as the Stream Deck forwarder and the Clip Mockup daemon ([ADR 0031](0031-clip-mockups-are-written-in-batches-through-a-local-daemon.md)). Not in the app server, and not in the **Sidecar**.
2. **It must survive both the app server and the Sidecar restarting.** A Recording Session runs for as long as Matt films, often an hour or more. In that time the app server restarts on a code change or a crash, and the Sidecar restarts with it under `pnpm dev`. Either one owning the ffmpeg processes would end the take mid-sentence. So `pnpm dev` and `pnpm start` start the service only when it is not already running, detached (`ensure-recorder-service.ts`), and never stop or restart it. Only Matt's main checkout starts it, as with the Stream Deck forwarder.
3. **It holds the camera only while the recorder is open for a Video.** Opening the recorder for a Video is what opens the Cam Link; closing it lets the device go, so OBS can still use it for an OBS Video. The recorder is open while an editor (or the thumbnail camera) on a New recorder Video listens to its events, and closes a few seconds after the last one goes (never mid-recording). Opening waits for the Cam Link's first real frame, tries three times, then asks for a replug and a Retry; a Cam Link another program holds is reported as "Close OBS first", and the service never closes OBS itself (`camera.ts`). Record is refused until the camera is live. The same port serves the raw camera and screen previews as MJPEG straight to the browser (`preview-feeds.ts`); the screen preview is a process of its own. The camera's preview process also sends a 1280x720 still feed, and `GET /still` serves its latest frame to the thumbnail camera in place of the OBS Virtual Camera (#2012); it refuses while the recorder is closed or recording.
4. **It never touches the database.** Its interface is one WebSocket (`protocol.ts`): open the recorder for a Video, record (with the **Silence Length** and a folder), stop, close, a stream of events, and a replay of a Recording Session's events after a given sequence number. Its durable record is each Recording Session's `events.jsonl` beside the Footage, every event numbered, so the app server, which writes the rows, can replay what it missed after its own restart and ingest each event once.
5. **One silence detector.** silencedetect runs inside the camera and mic process, on the mic audio that process writes, with the threshold and Silence Length the OBS path uses. Its speech events are in the mic file's time. The OBS path's live detector in the browser measures the same way (2026-10-12): it opens the same mic as both Recorders (`Voicemeeter Out B1`, found by label as the recorder service finds it, `app/mic-device.ts`) with Chrome's echo cancellation, noise suppression and auto gain control off, and runs silencedetect's rule on every channel, sample by sample (`silence-scan.ts`): a silence is every channel's peak below the noise level for at least the Silence Length. Before, it took channel 0's RMS from Chrome's default input with its processing on, and on the footage of 2026-10-10..12 it heard 76% of the audio as silence against ffmpeg's 64%, with 1735 silences against 993. Every detector reads its rule from one definition, `silenceRule` in `silence-detection-constants.ts`, so they cannot drift. Its threshold is that of the AV Calibration a Recording Session starts under, read once when it starts: Record (and the Stream Deck's prepare-record) carries that calibration, and the service refuses one without it, or one that is not fresh on its mic (ADR 0038).
6. **ffmpeg 8.0.1 only.** At start-up the service refuses any other version with how to install it. Since ADR 0049 that is CVM's own 8.0.1 build (`pnpm --filter @cvm/local ffmpeg:install`), not Gyan's. Newer builds need NVIDIA driver 610+ for NVENC. A change of NVIDIA driver since the last start only warns.
7. **A failure ends the Recording Session, never the Footage** (#2006). The camera process quitting, or the Cam Link sending no frame for 3 s, stops the whole Recording Session with a `camera-lost` event; the files and the Clips so far are kept. A Recording Session whose log has no stop when the service starts was cut off by a crash: the service stops any ffmpeg.exe still tagged with it (`stop-recorders.ps1`), remuxes each file that has no duration by stream copy (keeping the file as ffmpeg left it as `<name>.raw.mkv`, `footage-repair.ts`), ends a take still going where the repaired mic file ends, and logs `recording-crashed` (`crash-recovery.ts`). The app server replays every Recording Session the service reports recovered, or its database still has as recording, whenever the service greets it.

8. **The Stream Deck calls the recorder service, as the editor does** (#2004; Q14 in #1993). The forwarder (`stream-deck-forwarder/`) passes Record, Stop and one press per scene to the service as a `stream-deck` command, over one short-lived WebSocket per press and not over the hub, so an editor on an OBS Video never hears them. The service acts on whichever Video the recorder is open for; with none open, or when it cannot (camera not live, not recording), it does nothing and broadcasts `stream-deck-ignored` with the reason. A Stream Deck Record records with what the app server last prepared for the open Video (`prepare-record`: its editor's Silence Length and the recordings folder). The editor follows the service's events whatever started the action. Elgato's OBS plugin buttons stay for OBS Videos.

9. **The screen follows the Video's format** (#2056; PRD #2052). `open` carries the format. Landscape records the DELL, checked by name and size at Record. A Short records the Spacedesk virtual display, found by its display adapter's name (its monitor has no EDID name; `screens.ps1`): opening lists the screens, wakes Spacedesk only when its display is not listed (`app/spacedesk-wake.ts`, injected so tests never wake it), and needs it 16:9: the display is landscape 1920x1080, and the Short layout shows its left 1080x1080 square 1:1 above the camera band, as OBS's TikTok profile does (a portrait display was a wrong assumption, corrected in #2052's comments). The wake runs beside the command queue and the camera, and the state carries a screen status (`waking`, `ready`, `unavailable` with why); `retry-screen` checks again. With the screen unavailable a Short records camera and mic only (no screen process; stop, repair and crash recovery expect no screen file), and Record and scene switches refuse any scene that draws the screen.

## Why not the Sidecar

[ADR 0032](0032-background-work-runs-in-the-sidecar.md) puts background work in the Sidecar: work the author starts and walks away from. Recording is not that. Matt watches it, it has no end he can predict, and it is tied to devices on his desk. The Sidecar restarts with the app under `pnpm dev`, and a **Job** that dies with it is retried, which a lost take cannot be. ADR 0032 stands: its section 7 names the recorder service among the processes that start other processes outside the Sidecar.

## Why not the app server

The app server restarts on every change to server code under `pnpm dev`. Holding ffmpeg there would end the take each time. A WebSocket from the app server to the service has no such cost: the socket drops, the app server reconnects, and it replays from the last sequence number it saw.

## Consequences

- The service runs whatever code it started with. Picking up a change to it means stopping it by hand (`kill <pid>`, which closes the files with `q` first); `pnpm dev` then starts the new code. It is never restarted for you, because that would stop a recording.
- Its tests drive it through its WebSocket with the process launcher (`launcher.ts`) as the only fake: a scripted ffmpeg.exe. The real Cam Link, the DELL, the mic and NVENC are not tested in CI. The rig (#1992) proved them, and Matt's first real Recording Sessions watch them.
- Its state is `.data/recorder-service/` (the last NVIDIA driver seen, an index of Recording Sessions for replay) and its log is `.data/logs/recorder-service.log`, both at the repository root.
- The app server's half is the **recorder client** (`apps/local/app/services/recorder-client/`): one WebSocket per app server process, opened on first use and kept across dev reloads. It sends Record and Stop for the editor, puts the service's events back in `seq` order per Recording Session (asking for a replay over a gap), and saves what each means: a `recording_session` row on start and stop, Clips when speech ends (`placeSpeechAsClips`, skipping a take that Recording Session already has, so a replay saves nothing twice). The editor hears what was saved over `GET /api/videos/:id/recorder/events`. Only the main checkout's app server connects to the service; any other gets the dead port, as with the Stream Deck hub.
