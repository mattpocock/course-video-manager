# Background work runs in the Sidecar: the tab only enqueues and listens

A background job is work the author starts and walks away from: an export, a vertical Short, a post, a Course **Autofill**, a **Publish**, a Clip's transcription. Until this change each one was a single HTTP request, usually a server-sent event stream, and a browser queue (the Upload Manager) kept it alive. Closing or reloading the tab aborted the request, and the server interrupted the work. The job's state lived only in React memory, so nothing ran it again, and its failure was a toast that no log kept. [ADR 0024](0024-autofill-is-a-job-of-its-own.md) accepted that for the Autofill and named "a durable background worker" as the deferred next step. This ADR records that step. The full migration, batch by batch, is in `docs/plans/background-jobs-sidecar.md`.

## Decision

1. **Every background job is a Job, and the Sidecar runs it.** A Job is a row in `job`, and its history is the `job_event` rows, in the same Postgres as the data (`packages/core/db/schema-jobs.ts`). The browser (through `POST /api/jobs`, `routes/api.jobs.ts`), `cvm course publish` and `cvm footage transcribe` start one with `enqueueJob` (`apps/local/sidecar/job-specs.ts`), checked against `JOB_KIND_SPECS`. A running Job starts another only through `ctx.enqueue` (`sidecar/job-context.test.ts`). The **Sidecar** (`apps/local/sidecar/`) claims each Job, runs its kind's handler (`sidecar/kinds/`), logs it to `.data/logs/jobs/<job id>.jsonl`, and writes its **Job Events**. Every background job is a kind: `export`, `batch-export`, `render-vertical`, `youtube`, `youtube-shorts`, `buffer`, `ai-hero`, `skills-changelog`, `autofill`, `publish`, `transcribe-clips`, `transcribe-footage`, `duplicate-course` (a Course copied under a new name: its rows, then every Video's frames, WAVs and Video Files), and the Cloudinary image upload, `upload-images` with its `remove-local-images` (a local file goes only once its URL is in a body whose save is confirmed: `features/image-upload/image-upload-job.ts`).
2. **The tab only enqueues and listens, over one Job Event stream.** Each tab opens one `EventSource` on `GET /api/jobs/events` (`features/jobs/use-jobs.ts`). The app passes through the Sidecar's feed (`sidecar/job-event-feed.ts`): a snapshot of recent Jobs, then every new Job Event. The jobs reducer (`features/jobs/jobs-reducer.ts`) folds them into the rows the Upload Manager draws, and `job-event-hub.ts` hands the same stream to the video editor for Clip transcription. Closing the stream cancels nothing. The browser Upload Manager's own queue, reducer and retry path are deleted (#1930). `features/upload-manager/` now only draws Job rows and their ETA.
3. **Retries are copied, not invented** (Matt's decision 2). Each kind's attempts come from what the browser allowed, and are listed in `UPLOAD_MANAGER_POLICIES` and `CLIP_TRANSCRIPTION_POLICY` (`sidecar/retry-policy.ts`): an export and a vertical render get 3 attempts; a Batch export, an Autofill, a Clip transcription and a Footage transcription get 1. A Course duplicate (`COURSE_DUPLICATE_POLICY`) gets 2, not the browser's 1, so a run the Sidecar loses mid-copy resumes: its rows are one transaction, recorded as a Job Event and skipped once recorded, and a file already in place at its source's size is skipped. A Batch export Video that fails is handed on as its own `export` Job with 2 attempts, so it still runs at most 3 + 2 = 5 times. The rule lives once, in `packages/core/services/db-job-operations.server.ts`. A failed attempt goes straight back to the queue while attempts remain. A run the Sidecar lost (it died, or the Job's lease ran out) counts as a failed attempt (`recoverExpiredJobs`). A deliberate stop (a signal) puts the Job back at the same attempt (`returnJobToQueue`). When a Job fails for good, every Job waiting on it fails too (`failDependents`). The narrow retries inside a service (Dropbox HTTP, an export inside a Publish, Autofill's rate limit) stay where they were.
4. **Two lanes, both copied** (Matt's decision 3). `sidecar/lanes.ts` has a `default` lane with no limit, as the Upload Manager had none, and a `publish` lane that runs one Job at a time. The `publish` lane replaces the Publish's one-permit `courseVersionMutationSemaphore`. Limits on a resource inside a Job stay in the service: ffmpeg's permits, 6 exports at a time, Autofill's 6 Videos, Dropbox's upload pool and Whisper's 20, which a Clip transcription and a Footage transcription share, because the Sidecar builds one `WhisperTranscriptionService`.
5. **A post and a Publish never run again on their own.** Matt: "I definitely don't want reruns to happen on their own. Posting twice would be disastrous."
   - **Posts.** A posting kind (YouTube upload, YouTube Shorts, Buffer, AI Hero, Skills Changelog) is defined with `definePostingJobKind` (`sidecar/job-kind.ts`). It always gets `POSTING_JOB_POLICY`: exactly 1 attempt. No failure, stop or crash runs it again. A post that is cut off ends `interrupted`. The Sidecar then checks the service, read-only, to see whether the post went out (`sidecar/post-checks.ts`). Only the author's **Retry** runs a post again (`retryJob`, `POST /api/jobs/<id>/retry`). The server refuses a Retry when the run went out, when the author is retrying an older run, or when the Job it waits on did not succeed (`packages/core/services/db-job-posting.server.ts`).
   - **Publish.** A `publish` Job has 1 attempt and `neverRequeued` (`retry-policy.ts`). A stop or a crash ends it `interrupted`. If it got past **Submit**, its **Pending Version** waits on the publish page, where the author chooses **Promote** or **Discard** by hand (`features/publish/pending-recovery-banner.tsx`). `retryJob` refuses every kind that is not a post, so a Publish has no Retry. A new Publish is a new Job.
   - **Enforcement.** `isNeverReRun` (`job-kind.ts`) holds both cases in the Sidecar's settle and recovery code (`sidecar/sidecar.ts`). `sidecar/posting-kinds.test.ts` and `sidecar/publish-kind.test.ts` fail if either slips back.
6. **Spawning is the Sidecar's.** Everything that starts a process for background work is in the Sidecar's own layer (`sidecar/sidecar-layer.ts`), not the app server's `layerLive`. That covers the encodes (`ffmpeg-run.ts`, `ffmpeg-encode-commands.ts`), the Overlay renderer (`overlay-content-renderer.ts`), the vertical render (`render-vertical-video-service.ts`), Publish and Whisper (`whisper-transcription-service.ts`). The code that does this work asks for `SidecarContext` (`app/services/sidecar-context.ts`), and only the Sidecar's layer provides it, so a route that reaches it does not compile. Three guards hold the rest:
   - `apps/local/.dependency-cruiser.spawn.cjs` (run by `lint:boundaries`) refuses any path from `app/routes/` to a Sidecar spawner, the Sidecar's layer or a Job handler, and any `child_process` import outside `sidecar/` and the entry points named in 7.
   - `scripts/check-background-jobs.ts` counts streaming routes, browser drivers, `Command.make` calls and outbound network or AI calls (`network`: every use of the global `fetch` but `fetch("/…")`, the app calling itself, and of the AI SDK's `generateText`, `streamText`, `generateObject`, `streamObject` and `ToolLoopAgent`, a provider model's `doGenerate` and `doStream`, the OpenAI and Anthropic clients, Effect's `HttpClient`, Cloudinary's `uploader` and `api`) against a shrink-only allowlist, `scripts/background-jobs-allowlist.json`, with a reason for each file. `network` counts uses, not calls, so an alias (`const get = fetch`) or a namespace (`import * as ai`) counts too, and no file binds a `fetch` of its own. It covers all of `apps/local` but `sidecar/` and the dev scripts, `.tsx` included, plus `packages/` and `apps/remote`: a slow call the author walks away from is a Job.
   - `apps/local/.dependency-cruiser.network.cjs` (run by `lint:boundaries`) is `network`'s import half. A network or AI client package (`ai`, `@ai-sdk/*`, `openai`, `cloudinary`, `https` and the like) is imported only by the files on the `network` allowlist, which it reads, by the entry points named in 7 that call nothing, and by `sidecar/`, so no wrapper module carries a client past the count. `app/` reaches `sidecar/` only through `sidecar/job-specs.ts`, and never the dev scripts, since `network` does not scan them.
   - `pnpm run check` runs all three.
7. **What stays outside the Sidecar, by name.** Every file the guards in 6 let start a process, stream or loop outside the Sidecar is on this list, with why. None is work the author walks away from. `tests/background-jobs-guard.test.ts` fails if a file on `scripts/background-jobs-allowlist.json`, among the `child_process` entry points of `apps/local/.dependency-cruiser.spawn.cjs` or among the network client entry points of `apps/local/.dependency-cruiser.network.cjs` is missing here.
   Each file is named by its path from the repository root, and the test matches that path inside this section only.
   - **Streams and loops in the browser** (the allowlist's `sse-route` and `browser-driver`):
     - the chapter Autofill modal and its stream (`apps/local/app/features/video-editor/components/autofill-chapters-modal.tsx`, `apps/local/app/routes/api.videos.$videoId.autofill-chapters.ts`), because it is a conversation with the person watching;
     - OBS clip ingestion (#13, the loop in `apps/local/app/features/video-editor/obs-take-saver.ts`) and the wait for OBS's virtual camera (`apps/local/app/features/video-editor/obs-connector.tsx`), because both belong to a live **Recording Session**;
     - the New recorder's events for the editor (`apps/local/app/routes/api.videos.$videoId.recorder.events.ts` and the `EventSource` in `apps/local/app/features/video-editor/use-cvm-recorder.ts`), for the same reason: they record nothing and cancel nothing, and the recorder service and the app server's recorder client record and save whether anyone listens. The thumbnail camera listens through the same `EventSource` while its modal is open on a New recorder Video. Their listening only keeps the recorder open for that Video (the Cam Link and the previews), and a recording outlives it (ADR 0034).
     - the AV Calibration page's level meter (`apps/local/app/routes/api.av-calibration.meter.ts` and the `EventSource` in `apps/local/app/features/av-calibration/use-level-meter.ts`): listening is what runs the recorder service's mic-only ffmpeg.exe, and the last listener going stops it, so it must end with the tab, the opposite of a Job.
     - the Storage page's scan (`apps/local/app/routes/api.storage.scan.ts` and the `EventSource` in `apps/local/app/features/storage/use-storage-page.ts`, #2107): a read-only count for the person watching the page, which must stop when the tab goes so it never keeps reading a slow USB drive in the background (ADR 0041). Moves are Jobs; the scan is not.
     - the per-bucket page's listing (`apps/local/app/routes/api.storage.buckets.$bucketId.files.ts` and the `EventSource` in `apps/local/app/features/storage/use-bucket-page.ts`, #2108): the same read-only walk kept to one Storage Bucket, for the person watching the page, stopping when the tab goes.
   - **`Command.make` in the Sidecar's spawners** (the allowlist's `spawn`, Sidecar only, as in 6): `apps/local/app/services/ffmpeg-run.ts`, `apps/local/app/services/ffmpeg-encode-commands.ts`, `apps/local/app/services/overlay-content-renderer.ts`, `apps/local/app/services/render-vertical-video-service.ts` and `apps/local/app/services/whisper-transcription-service.ts`. Each asks for `SidecarContext`, and no module a route reaches may import it.
   - **`Command.make` on the app server** (the allowlist's `spawn`):
     - `apps/local/app/services/ffmpeg-commands.ts`, shared by the app server and the Sidecar. On the app server, most of its work is the live Recording Session: OBS clip ingestion (`append-from-obs`, `clip-service-handler.helpers.ts`) probes the frame rate and runs silence detection on the recording OBS is writing (`video-processing-service.ts`, `silence-detection.ts`); when the editor names that file, from a second before the end of the last Clip taken from it. Beside that, it grabs one frame for the Article Writer's screenshot (`api.videos.$videoId.capture-screenshot.ts`). On the AV Calibration page it runs silence detection over one stored calibration's mic file (about a minute) to draw its review timeline (`api.av-calibration.$calibrationId.timeline.ts`), while the page waits. In the Sidecar the same calls serve the export's duration probe, the vertical Short and Footage transcription, which runs silence detection over a whole recording. The encodes are in `ffmpeg-encode-commands.ts`;
     - `apps/local/app/services/video-processing-service.ts`: a Clip's first or last frame for a thumbnail (`clips.$clipId.first-frame.ts`, `clips.$clipId.last-frame.ts`), each one request the author's page waits on.
     - `apps/local/app/packages/clap-step/lib/ffmpeg.ts`: the AV Calibration page's clap step (#2137; `api.av-calibration.$calibrationId.clap-step.ts`, `.frame.$frame.ts`, `.preview.ts`) reads the mic around the clap, one camera frame as a JPEG, or a 2 s clip for Play (NVDEC and NVENC, libx264 on the CPU when there is no usable GPU; a clear error, not the CPU, when NVENC has no free session), each while Matt waits on the page.
   - **`child_process` on the app server and in `cvm`** (`INTERACTIVE_CHILD_PROCESS` in `.dependency-cruiser.spawn.cjs`):

     - `apps/local/app/services/open-folder-service.ts`: "Open folder" (`explorer.exe`) and "Open in VS Code" (`code`), from `api.videos.$videoId.open-folder.ts` and `api.videos.$videoId.open-in-vscode.ts`;

No route and no Job reaches it;

A run cut off by a restart resumes from the chunks it cached beside the file (`sidecar/footage-chunk-cache.ts`). The interactive AI streams (the Article Writer, completions) are conversations too, and stay.

## What the tab still decides

- **Toasts are reducer decisions carried on effects.** When a Job settles, the jobs reducer builds the toast (`features/jobs/job-succeeded-toast.ts`) and puts it on the `show-job-succeeded-toast` effect. The handler only draws it, and never reads state (#1926).
- **A toast fires only for a settlement this tab heard live.** When the feed gets its first subscriber, it re-sends the last 60 seconds of events. A Job Event at or below the snapshot's cursor updates the row but never toasts (`jobs-reducer.ts`, `caughtUp`, #1938). So a new tab does not re-announce an export that finished, or was dismissed, before it opened.
- **Clip transcription never toasts and draws no row.** The Clip shows its own state. The editor's clip reducer folds the `transcribe-clips` Job's `clips-started` and `clip-settled` events (`features/video-editor/clip-state-reducer-transcription-jobs.ts`).
- **The ETA comes from Job Event timestamps.** A row's stage durations and rates come from each event's `at`, so a reopened tab replays the same countdown. Stage history is read from `job_event`, not localStorage: `GET /api/jobs/stage-history` returns the newest 20 succeeded Jobs of each kind (`packages/core/services/db-job-stage-history.server.ts`). A fresh browser therefore has an ETA from its first export (#1933, #1938).

## Considered and rejected

- **A per-checkout SQLite job table.** It would isolate every checkout for free. But Jobs could not join to the Videos and Courses they work on, `cvm` could not see them, and the domain would be split across two databases. The job table is in the same Postgres. A verify-cvm clone gets its own table, and the worktree guard (`packages/core/db/connection-guard.ts`) already stops a worktree from writing to production.
- **An `ai` lane** (one Autofill at a time). Nothing held a second Autofill back in the browser, so a lane would have been a new limit. An Autofill runs in the `default` lane, and its 6 Videos at a time stay in the service.
- **Automatic Promote or Discard of an interrupted Publish.** The first plan reconciled a Pending Version on its own after a crash. That would be a new policy for the one Job that can leave the course half-published. The author still decides, from the receipt the publish page shows.
- **Re-running a cut-off post, as the browser did.** The browser retried a failed post up to 3 times, and ran one again after a server death, when the post might already have landed. Copying that exactly was decision 2; decision 5 overrides it for posts. A Publish already had 1 attempt, and `neverRequeued` adds that a stop does not put it back.
- **Re-transcribing Clips stuck in `transcribing`.** Matt's call: the sweep (`sidecar/stuck-clip-sweep.ts`) marks a Clip that no live `transcribe-clips` Job holds as `failed`, and the author re-transcribes it by hand. The sweep never enqueues a Job and never calls Whisper (#1925).

## Consequences

- **Closing the browser never stops a Job.** Reopening a tab shows it from the snapshot, still running or settled.
- **Work waits while the Sidecar is down.** Enqueue still succeeds, because a Job is a row, and every page shows "Background jobs are stopped" (`features/jobs/sidecar-down-banner.tsx`). Jobs start when the Sidecar comes back. `pnpm dev`, `pnpm start` and every verify-cvm run start one.
- **A new kind of background work is a Job kind:** its params in `sidecar/job-params.ts`, a handler under `sidecar/kinds/`, one line in `JOB_KINDS` (`sidecar/job-kinds.ts`) and its spec in `JOB_KIND_SPECS`. A new streaming route, browser loop or spawn in a file the guards scan fails `check`, unless it is added to the allowlist with a reason.
- **A post or a Publish that is cut off needs a person.** That is the price of never posting twice. An interrupted post shows its post-check verdict and a Retry. An interrupted Publish sends the author to the publish page.
- **Supersedes ADR 0024's deferred note.** The Autofill runs as an `autofill` Job (`sidecar/kinds/autofill.ts`) and no longer stops with the tab. The rest of ADR 0024 stands.
